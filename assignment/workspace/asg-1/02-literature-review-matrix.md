### 2.2. Review Synthesis

| ID | Relevance to this review | Critical appraisal | Future implications |
|---|---|---|---|
| M07 | Provides the authoritative basis for explaining virtual-thread behavior and limits. | It is a design specification, not comparative empirical evidence, and the live page can be updated. | Combine its design claims with current framework, database, tail-latency, and resource experiments. |
| M08 | Directly compares the three Java request-processing models discussed in the paper. | One Quarkus/Netty application, preview-era virtual threads, tight resource limits, and few scenarios restrict transferability. | Retest current JDK, Quarkus, and Netty releases with broader workloads and framework integrations. |
| M09 | Connects virtual-thread behavior to specific database dependencies. | Single laptop, small dataset, average latency only, and no TPS, tail latency, CPU, memory, cloud, or container evidence. | Use production-like infrastructure, larger workloads, repeated statistics, and end-to-end metrics. |
| M10 | Adds empirical throughput, latency, CPU, and memory evidence for reactive Java processing. | One support application and controlled scenarios; maximum reported gains are not general averages. | Replicate with more databases, hardware, production traffic, and data-intensive workloads. |
| M11 | Supports measuring GC through application throughput, latency, CPU, and memory rather than pause time alone. | Distillation provides a lower bound rather than exact intrinsic cost; results use OpenJDK 17 and benchmark workloads. | Apply the method to newer runtimes, collectors, and production-style workloads. |
| M12 | Provides a workload-specific way to reason about GC selection. | Exact-selection accuracy is modest; tests used OpenJDK 15, one environment, and mostly CPU-intensive benchmarks. | Rebuild selection data for newer JDKs and add reliable I/O and latency-sensitive workloads. |
| M13 | Demonstrates that GC design can change Java throughput and extreme tail latency. | LXR was a prototype on OpenJDK 11 and lacked several production runtime features. | Port and tune it on newer JDKs, complete missing features, and test production-scale services. |
| M14 | Explains JVM warm-up and startup capacity costs in frequently scaled Java services. | Only Eclipse OpenJ9, three applications, and a high-speed datacenter network were evaluated; reported values are maxima. | Test other JVMs, higher-latency networks, FaaS, and broader microservice workloads. |
