# Interview Notes

This file stores interview questions, answer examples, and technical talking points collected from videos, articles, or other learning sources.

## 1. Question Group 1

### 1.1 High Concurrency Experience

🎯 我问：你没有大厂高并发项目经验，怎么证明自己能扛住业务压力？

💡 她答：虽然没做过千万级 QPS 的应用，但我在个人项目里做过 JVM 性能深度优化。一开始接口响应要 2 秒，我通过 Java 内存模型分析、GC 日志排查、线程池参数调优，还手写了性能监控脚本来采集 Full GC 频率和接口耗时。最终把接口响应时间优化到 200ms 以内，Full GC 频率从每小时 10 次降到每天 1 次。整个过程我整理了完整的性能测评报告、JVM 参数对比文档和问题排查记录，都在我的项目复盘里。

### 1.2 Deep Java Direction

🎯 我问：Java 技术方向这么多，你最深入哪块？

💡 她答：我主要聚焦 "Java 并发编程、JVM 底层原理和微服务架构" 这三个方向。比如并发方面，我研究过 AQS 源码、synchronized 锁升级过程和 ConcurrentHashMap 的分段锁机制；JVM 方面，我能系统分析内存分配策略、手写类加载器、解决 OOM 问题；微服务上，我从零搭建过 Spring Cloud 项目，做过服务熔断降级和分布式事务方案对比。

### 1.3 CPU Spike Or API Timeout

🎯 我问：线上服务 CPU 飙升/接口超时，你会怎么排查？

💡 她答：我会分层定位：首先用 top 和 jstack 定位线程问题，看是哪个线程占满 CPU；接着用 jstat 和 jmap 分析 GC 情况和堆内存快照，排查是否有内存泄漏；最后结合链路追踪工具看调用链耗时。之前我就用这个方法，定位到一个死循环导致的 CPU 飙升，还发现了一个因未关闭的连接池引发的内存泄漏，都通过代码重构和连接池配置优化修复了。

### 1.4 Big-Company Middleware

🎯 我问：怎么看待大厂的自研中间件，比如内部的 RPC 框架或 MQ？

💡 她答：我研究过像 Dubbo、RocketMQ 这类开源中间件的核心原理，也看过大厂如何基于它们做二次开发。它们通常在服务发现、负载均衡、消息持久化上有深度定制。我觉得 Java 开发不能只停留在 Spring 应用，理解底层通信协议、线程模型和存储机制，才能更好地做技术选型和解决分布式系统难题。

## 2. Question Group 2

### 2.1 现货交易系统设计

- 问题：如何设计一个支持高并发的现货交易系统？
- 答案：
  - 订单处理：Redis 缓存订单簿，Kafka 异步处理交易流水。
  - 数据库优化：MySQL 分库分表（按用户 ID 哈希），冷热数据分离（ES 存储历史订单）。

### 2.2 撮合引擎核心原理

- 问题：撮合引擎如何实现价格优先 + 时间优先？
- 答案：
  - 订单簿结构：买单队列（价格从高到低排序），卖单队列（价格从低到高排序），双向链表实现。
  - 匹配算法：新买单与卖单队列头部匹配（若买单价格 >= 卖单价格，则成交）。
  - 性能优化：全内存撮合（Disruptor 无锁队列），TPS 可达 100 万+/秒。
  - 扩展：支持市价单、限价单、IOC（立即或取消）等订单类型。

### 2.3 Java 并发与性能

- 问题：如何保证撮合引擎的线程安全？
- 答案：
  - 无锁设计：Disruptor 环形队列避免锁竞争。
  - 线程绑定：Linux CPU 亲和性（affinity）绑定核心，减少缓存失效。

### 2.4 第二轮技术面

#### 2.4.1 智能合约集成

- 问题：Java 如何调用币币交易的链上清算合约？
- 答案：
  - Web3j 库：部署 ERC-20 合约处理资产兑换，事件监听（如 Transfer 事件）异步更新余额。
  - Gas 优化：批量提现请求合并处理，降低 Gas 成本。
  - 安全：防重入攻击（Checks-Effects-Interactions 模式）。

#### 2.4.2 系统设计题

- 问题：设计一个支持 10 万 TPS 的币币交易系统。
- 架构要点：
  - 撮合集群：按交易对分片（BTC/USDT 独立引擎），避免热点。
  - 缓存策略：Redis 缓存委托账本（OrderBook），Guava 本地缓存行情快照。

#### 2.4.3 区块链基础

- 问题：UTXO 模型 vs 账户模型，交易所如何选型？
- 答案：
  - UTXO（比特币）：隐私性好，但复杂查询困难。
  - 账户模型（以太坊）：易于状态管理，适合智能合约。

### 2.5 面试官深挖点

- 性能极限：“如何将撮合延迟从毫秒优化到微秒？” -> 内核旁路（DPDK）+ 物理网卡绑定。
- 安全陷阱：“如何防止订单簿被恶意刷单？” -> 速率限制 + 行为分析模型。
